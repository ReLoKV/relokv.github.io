Measurement Protocol

This page describes the reproduction requirements for the experimental groups. Runnable implementations, commands, checkpoints, traces, and measured outputs are not included in the current release.

  1. Record device settings, runtime revision, base model, tokenizer, prompt template, adapter versions, and generation settings for every run. The environment inventory template lists the required metadata.
  2. Fix request inputs and order, physical-byte budgets, and maximum background-work budgets across comparable methods. Preserve version checks and recovery dependencies in every valid policy.
  3. Measure TTFT from request arrival to the first generated token. Distinguish backend stage timing from complete service latency. Record earlier preparation and its interference separately.
  4. Include anchors, deltas, complete KV, metadata, and workspaces in physical-memory accounting. Do not sum overlapping stage durations as wall-clock latency.
  5. Record independent process replays and predictor training seeds separately. The initial evaluation plan uses at least three process replays for representative configurations and three predictor seeds, with repetition adjusted by observed variability.
  6. Retain failed, timed-out, and crashed runs. Missing values are not zero. Assess uncertainty using users, traces, or independent runs rather than treating correlated requests as independent users.
  7. Provide input manifests, actual commands, expected output files, plotting scripts, and validation criteria with each executable release. Label reimplementations of related mechanisms explicitly.

E01–E03: Workloads and Baselines

  • E01: document behavior and text sources, task/adapter mappings, document deduplication, and user/time split boundaries.
  • E02: check conversation-history append behavior, negative reuse cases, return intervals, and whether future records change earlier decisions.
  • E03: pin the environment and verify no-reuse and exact same-LoRA prefix baselines against recomputation.

Expected outputs include workload statistics, token and return-distance distributions, an environment manifest, baseline correctness checks, and timing-boundary definitions.

E04–E06: Prediction and Effective Preparation

  • E04: compare simple and learned predictors under the same visible history, including switch-only samples, time-order diagnostics, and online overhead.
  • E05: compare demand-only preparation, adapter-only preload, and adapter plus legal historical-KV recovery with fixed state-management rules.
  • E06: vary candidate counts, preparation windows, budgets, and controlled prediction errors; record wasted work and foreground interference.

Expected outputs include Top-k/MRR summaries, split and checkpoint metadata, request-level coverage, preparation-to-consumption event links, cancellation and expiry, and TTFT/ITL measurements.

Predicting an adapter is not a KV hit. The candidate must pass session, exact-prefix, dependency, version, readiness, and consumption checks. Oracle permissions must be explicit; future new text is not available by default.

E07–E09: Grouping, Anchors, and Deltas

  • E07: compare grouping schemes under matched requests and budgets, estimating relations and structure from training/calibration data only.
  • E08: vary anchor selection while holding grouping and request order fixed; record the adapter-pair sampling plan.
  • E09: compare complete KV, direct complete-KV quantization, and anchor-delta representations at comparable task quality.

Expected outputs include separate K/V error distributions, search overhead, recovery success, construction and restoration times, full-family storage, temporary peaks, and downstream quality.

First-construction costs include the real target KV and any extra prefill. High cosine similarity alone does not establish equivalent output quality.

E10–E12: Lifecycle and Cache Management

  • E10: verify actual transitions between complete and compressed states, host-side availability, and restored GPU-ready states.
  • E11: compare blocks, leaf eviction, session paths, family dependency closure, and joint management under the same physical budgets.
  • E12: ablate prediction, frequency, dependency impact, and preparation-cost scoring; tune on validation data and lock test parameters.

Expected outputs include usable continuous-prefix coverage, actually released bytes, metadata and restoration peaks, dependency audits, eviction/cancellation records, and latency.

Dependency protection remains enabled. Shared parent memory is counted once. Include cases where a cold anchor supports hot children rather than requiring an entire family to remain resident.

E13–E15: Background Execution

  • E13: separate kernel fusion, multilayer task organization, and transfer effects in local benchmarks before integration.
  • E14: compare serial work, stream organization, layerwise recovery, and load-aware deferral under idle, prefill-heavy, decode-heavy, and bursty conditions.
  • E15: compare serial and adapter-aware batches with matched request sets, ordering semantics, and memory budgets.

Expected outputs include CUDA event timelines, host wall-clock timings, synchronization and waiting, foreground slowdown, background backlog, invalid preparation, memory peaks, and energy.

Real inference results are needed to establish overlap benefits. Stream priority does not guarantee preemption or freedom from bandwidth contention.

E16–E18: End-to-End Evaluation

  • E16: replay sequential and parallel workloads against strong baselines at representative physical-memory budgets.
  • E17: remove modules separately and evaluate interactions among prediction, joint KV management, and asynchronous execution.
  • E18: vary adapter count, context length, return distance, switch probability, arrival rate, and preparation budget in representative stress cases.

Expected outputs include TTFT/ITL distributions, throughput, physical peaks, energy, quality, failure rates, SLO outcomes, and run-level paired comparisons.

Include low-reuse and wrong-prediction conditions. Distinguish original implementations from mechanism reimplementations.

E19–E20: Quality, Energy, and Correctness

  • E19: compare exact reuse and restored states with the same target adapter's original full KV using logit, task-quality, and output checks with recorded tolerances.
  • E20: record sustained-run power, temperature, backlog, leaks, errors, and completion outcomes; exercise version changes, anchor eviction, cancellation, bursts, and buffer synchronization.

Expected outputs include quality-space-latency comparisons, paired uncertainty, total and explicitly defined idle-adjusted energy, and directed correctness reports.

Acceptance criteria are chosen before testing. Non-significance does not establish equivalence. Energy measurements specify whether foreground work, background work, and waiting are included.
